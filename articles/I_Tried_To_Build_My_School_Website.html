我尝试给学校做了个官网……

2026年9月14日
阅读时间：6 分钟
前端 Web 校园 折腾

事情的起因特别土：上学期班会上，班主任随口说了一句"我们学校的网站还是十几年前做的，你们谁懂这个"。我举了手。

三个月之后，我的电脑里多了 40 多个叫 final_v3、final_v3_真的最终版 的文件夹，还有一份被改了七遍的配色方案。这篇文章就是给这段经历的交代：我做对了什么、做错了什么，以及一个学生想给学校做官网，到底会遇到什么。

一开始我以为这活儿很简单

这个博客就是我自己手写的 HTML + CSS + JS，纯静态，没有框架，部署也简单。所以我当时的判断是：学校官网嘛，无非首页、学校简介、师资队伍、新闻公告、招生信息、联系我们，六个页面，一周能交。

第一次跟信息组老师开会，我列了需求清单，对方连连点头。现在回头看，那次会议最大的问题是：点头不代表有共识，只代表我说的他都没听懂。

需求是怎么一步步长出来的

真实的需求变更记录大概是这样的：

轮次老师说的实际要做的事我的心情
第一轮"就按你说的来"六个静态页面轻松，觉得自己效率惊人
第二轮"首页太空了，加点东西"通知跑马灯、校园风光轮播、数据统计、快捷入口一周变成三周
第三轮"能不能加个飘动的校徽"委婉地、反复地解释为什么 2010 年的审美和自动播放的音乐不适合 2026 年的网站学会了怎么把"不行"说成"这样做会更好"
第四轮"内容我们自己能改吗"重新设计内容维护流程，写文档、录视频、教操作这才是真正的大工程
第五轮"要和原来的系统打通"我卡住了，这超出了我能做的范围认清了边界

第三轮那条我想多说一句。"飘动的校徽""自动播放的背景音乐""访客计数器"（最好是那种会动的数字）——后来我明白了，这不是审美问题，而是提需求的人不负责落地。我的解决办法不是硬顶回去，而是把代价翻译成对方在意的语言："这个插件有 800KB，家长用手机打开会白屏三秒。"这句话比"这个很土"有效一百倍。

技术其实是最轻松的部分

真写起来，难点都不在"会不会写代码"，而在"有没有想清楚给谁用"。

第一，家长几乎全用手机看。 我做的第一件事是打开手机的 4G 网络去体验同类学校网站，一半以上的首屏加载超过五秒。所以我定了几条硬规矩：不引第三方 UI 框架、不用图标字体、图片全部压缩并加 loading="lazy"，字号用 clamp() 做流体缩放，让中老年用户不用双指放大：

/* 正文在手机和桌面之间平滑缩放，最小 16px，最大 19px */
                        body {
                            font-size: clamp(16px, 1.1vw + 12px, 19px);
                        }
                        
                        /* 卡片列表：手机一行，平板两行，桌面三行 */
                        .card-grid {
                            display: grid;
                            gap: 20px;
                            grid-template-columns: repeat(auto-fit, minmax(260px, 1fr));
                        }

第二，老师发来的图片有 30 张，单张 4MB。 用任何在线工具批量压到 200KB 以内、转成 WebP，这一步让首页从 8MB 降到 900KB，比任何前端优化技巧都管用。

第三，也是最重要的一条：内容得老师自己能改。 我最早的方案是"你把文字发我，我来改"，两周后就发现这是给自己挖坑——凌晨十一点收到微信"首页第三行那个'的'改成'了'"。后来我把所有可变内容抽成几个 JSON 文件，配上一份图文教程和一小时的培训，问题基本解决了。

我踩过的坑

  • 域名和备案比写代码慢得多。 域名十分钟就能买好（不过未成年注册要用家长的身份），备案和 HTTPS 证书流程要走很久，学校官网还牵扯单位资质。如果想做，这件事要第一个启动，别等页面写完才想起来。
  • "谁能发布"是个责任问题，不是技术问题。 公告发错了谁负责？这个问题的答案决定了后台要做成什么样。我最后做的是最简单的方案：编辑者只能提交草稿，审核通过后才发布。
  • 别用框架。 我想过用某个流行的前端框架，后来算了一下：为了六个页面引入一整套构建工具链，下一个接手的人（很可能还是学弟学妹）要先学会装 Node 才能改一行字。纯静态 HTML 的维护成本在这里是压倒性优势。
  • 备份。 我有一版被自己的误操作覆盖过，从那以后每次改完都先 git commit。

结果：它没能正式上线

这就是标题里那个省略号的含义。最后卡在两件事上：一是长期维护的人是谁——再过一两年我就要毕业了，没人接手的话，这个站会变成第二个"十几年前做的网站"；二是学校原有系统那边有它自己的技术栈和流程，我一个学生推动不动。

所以它现在的状态是：一个能跑、能演示、文档齐全的原型，躺在学校信息组老师的电脑里。说不失落是假的，但我也想通了：一个学生能交付的最有价值的东西，不是那个网站，而是"这件事可以这样做"的证明。

如果你也想给学校或社团做个站

五条我觉得最有用的建议：

  1. 先问"谁维护"，再问"什么时候要"。 这两个问题的答案会直接改变你的技术选型。
  2. 别上框架，别上数据库。 静态站 + JSON 内容文件，是这个场景下的最优解。
  3. 把"改内容"当成第一需求来设计，而不是最后补一个后台。
  4. 准备好拒绝的话术。 用加载速度、手机流量、维护成本这些对方听得懂的理由，代替"这个不好看"。
  5. 上线才是开始。 如果真上线了，记得写好交接文档，那是对下一个人的善意。

结语

这三个月里，我写的前端代码可能只占全部工作量的三分之一，剩下的时间花在开会、画草图、压缩图片、写教程、以及反复解释"为什么飘动的校徽不好"上。但它确实教会了我一件在课堂上永远学不到的事：技术方案的价值，取决于它能不能被真实的人长期使用下去。

如果你们学校也有个十几年前的网站，我建议你举手。哪怕最后没上线，这件事也值得做一次。
